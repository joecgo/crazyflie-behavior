# Backlog #5: Hide-and-seek: open design questions

The row's history, moved from the [decision backlog](../decision-backlog.md) on 2026-11-16. The row keeps the open question.

**Hide-and-seek: open design questions** ([ADR-0016](../decisions/0016-first-game-hide-and-seek-drone-lands.md)). (a) **Choosing a hiding spot:** candidate spots on the map, kept only if a line-of-sight test from the launch point through the map hits at least one wall (later: test from several points across the waiting area, and a setting for how many walls), reachable, with 25 cm clear in every direction ([ADR-0073](../decisions/0073-landing-drift-accepted-25-cm-clearance.md)), and a flat floor to land on; scored by one plain function, like an EQS query without the framework. (b) **The hiding flight:** path planning on the map, and its time limit. (c) **Found detection:** thresholds for the down reading and the motion sensors (accelerometer and gyro log variables), and telling a pickup from a bump. (d) **Starting a round:** the adult's start action (a key on the PC?), checks before takeoff (the drone resting still on the launch point), re-arming, and the estimate reset ([ADR-0054](../decisions/0054-a-fresh-estimate-for-every-take-off.md): a behavior requests it on the floor and takes off a tick or more later; built with ADR-0054's code). (e) **Reactions:** LED patterns through the `led.bitmask` parameter (found; hints; an error shown in red), hint chirps from the Buzzer deck ([ADR-0017](../decisions/0017-hint-chirps-from-buzzer-deck.md); the chirp command is [ADR-0053](../decisions/0053-buzzer-commands-and-a-chirp-hover-test.md)), and the fanfare from the PC. The override hides the firmware's own LED warnings, such as low battery. (f) **The launch point:** a pad marked so the drone always sits in the same place, facing the same way. (g) **Battery:** rounds per battery, and when to swap. (h) **Handling by a child:** supervision, and checking the propellers are seated before each round. Stock firmware arms itself, so a landed drone is always armed ([ADR-0037](../decisions/0037-disconnect-does-not-disarm.md)): only our code not sending flight commands keeps its motors still. Options: turn auto-arming off in our own firmware build, so a disarm after landing holds (a second step a bug must hit, but not independent of our code), or a physical barrier such as unplugging the battery before the child handles it. (i) **Build order (suggested, not decided):** first a full loop with no map (fly a short way, land, found reaction), then the mapping run, then choosing hiding spots.
