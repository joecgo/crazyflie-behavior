01

The Adapter

Above the Crazyflie adapter, the code uses the project's own types and generic words: range readings, a position estimate, take off, land. Below it is Bitcraze's world: cflib, the Crazyradio and the drone's firmware. The adapter is the only code in src/ that imports cflib, and a fitness function fails continuous integration if anything else does.

Why it's built this wayWhy an adapter at all?

The project started before the drone was bought. Behaviors had to run and be tested with no hardware, then run unchanged on the real drone. If behaviors called cflib directly, nothing would run without a drone, and cflib's threading and blocking quirks would leak into every behavior.

So behaviors talk only to the drone interface, and adapters implement it: a mock adapter for tests and development, and the Crazyflie adapter for flights. cflib's quirks are solved once, in one place.

ADR-0002ADR-0008, the interface
Why it's built this wayWhy Crazyflie-focused, and not generic?

The Crazyflie is the only drone, and no other can be tested. So the interface is designed for it alone, but uses a generic name wherever most drones share the idea: range readings, position estimate, arm, take off, land. Crazyflie-only ideas (decks, log blocks, radio addresses, cflib's units) stay inside the adapter.

The accepted risk: some shapes are still Crazyflie-shaped, such as five fixed range directions. Another drone would likely become a separate project.

ADR-0006
Python noteAn abstract class, and with for a guaranteed landing

DroneInterface is an abstract base class: a method marked @abstractmethod is like a pure virtual function in C++, and Python refuses to create an object of a class that leaves one unwritten.

It also defines __enter__ and __exit__, so a program writes with drone:. Python calls __exit__ when the block ends, even when it ends with an error, much like a C++ destructor in RAII. Here that means disconnect() always runs, and it lands a drone that may be flying.

MoreWhat RAII is

RAII, "resource acquisition is initialization", is a C++ habit: an object takes a resource, such as a file, a lock or a network connection, when it's created, and gives it back in its destructor. C++ runs the destructor whenever the object goes out of scope, even when an error is thrown, so the resource can't be forgotten.

Python doesn't promise when an object's cleanup runs, so it uses with blocks for the same job. Here the resource is the radio link, and giving it back means landing first.

02

The Parts

The adapter is a package of nine modules: in Python, each file is a module, and a folder of them is a package. adapter.py is the main one. Four import cflib and run pyright, Python's type checker, in its basic mode. The other five don't import cflib, and all five are type-checked strictly. Four of those are tested without cflib. Take-off and landing is still tested through the adapter, with cflib's objects mocked, until backlog #158.

MoreWhy connect() builds every part afresh

Between two links, the drone may have landed, been moved or rebooted. So anything a part remembers from the last link may be wrong now. Kept, it would do harm:

  • A landing left under way would carry on, on a drone that may already be on the floor.
  • Old telemetry would pass the wait for the first telemetry, so the first snapshot would show the old drone, not this one.
  • A setpoint stream the drone stopped following long ago would still count as running.

So connect() starts by building every part new, with the same function __init__ uses, _build_parts(), and the new link learns everything again from the drone. A part made a moment ago has nothing to carry over, so no field can be missed, as one could be in a list of fields to reset.

The order inside _build_parts() matters: take-off and landing keeps the commands part it's given, so it's built right after the commands part.

Python noteWhy the parts get lambda: self._link.crazyflie

A lambda is a small unnamed function. The commands part stores this one as current_crazyflie and calls it whenever it needs the drone. Each call reads self._link afresh, so it always returns the current link's drone, like a C++ lambda that captures this rather than a copy of the pointer. Callable[[], Crazyflie] is its type: a function that takes nothing and returns a Crazyflie, like std::function<Crazyflie*()>.

Why not keep the buffer itself? In Python every variable holds a reference to an object, much like a C++ pointer, and passing it copies nothing. But connect() doesn't change the telemetry buffer in place. It replaces it twice: first with a new log blocks part, which makes a new buffer, then, after the estimate reset, with a new buffer in that same part. A part that had kept its own reference would still point at the old buffer, which nothing writes any more, the way a C++ pointer copied from owner->buffer still points at the old object after the owner swaps in a new one. Its values would only grow older, and a high-level move would aim at an old position. So every part looks up the drone and the buffer through a lambda on every call, and keeps neither.

Python noteA Protocol: how take-off and landing sends without cflib

A Protocol is like an interface: it lists the methods a type must have. The difference is that a class never declares that it implements one. Having the methods is enough, much as a C++ template accepts any type that has the methods it calls.

Take-off and landing declares FlightCommands: just the five sends it makes. The commands part has more, such as the buzzer's. Its class is written as class CrazyflieCommands:, with no mention of FlightCommands, where C++ or C# would write class CrazyflieCommands : FlightCommands. Pyright still checks the fit, at the line where the adapter hands the commands part to take-off and landing. Delete stop_motors from CrazyflieCommands, and pyright reports an error on that line: "stop_motors" is not present.

Python noteStrict and basic type checking

Python doesn't check types when it runs. Pyright reads the type hints and checks them before the code runs. The project sets its strict mode for all its Python, tests included, and a file can turn it down only with a comment. cflib has no type hints, so the four modules that use it switch to basic mode with one comment on their first line. Everything they hand to the rest of the project is fully typed.

MoreHow the rules are enforced: four fitness functions

Fitness functions read the code instead of running it, and fail continuous integration when a rule breaks. Their import scanner, import follower and comment scanner each have tests of their own.

  • Only the Crazyflie adapter imports cflib. 209-217
  • Inside it, only the four named modules do. A module that starts or stops importing cflib changes the list, so the change shows in review. 220-225
  • Take-off and landing reaches no cflib, not even through another module. 228-233
  • Nothing turns pyright's strict mode down for take-off and landing. 236-242
Why it's built this wayWhy split the adapter, and why here?

The adapter was once one class of 1,421 lines. Size alone is no reason to split a module: parts that share state, dependencies and reasons to change belong together. The project splits a part out only when one of five tests is true of it: it needs fewer dependencies than the file, another module needs it, it runs on a different thread, it has its own state and invariants, or it changes for a different reason.

Take-off and landing passes four of the five tests (1, 2 once the mock adapter runs it, 4 and 5). The log blocks part and the link part pass 3 and 5. The commands part passes 4 and 5.

03

Two Threads

Telemetry arrives on cflib's receive thread, whenever the radio delivers it. Decisions run on the tick's thread, 20 times a second. The two meet in one place: the telemetry buffer, guarded by the only lock in the data path. Each tick copies it into a snapshot, and every value carries the time it arrived, so any reader can tell how old it is.

MoreThe state block's 26 bytes

A log block carries at most 26 bytes of variables. The state block fills all 26: the position and velocity estimates as six 4-byte floats, and the drone status as a 2-byte bitfield. Because the three share one packet, they always come from the same moment, and a lost packet loses all three together, so they go stale together.

MoreStamped values: two clocks on every reading

Every value in a snapshot is a stamped value. Staleness uses the arrival time, on the PC's clock. The drone's own timestamp is kept for measuring latency, for recording and for replay.

Python note. @dataclass writes the constructor and comparisons for you. frozen=True makes every field read-only after construction, and slots=True stops new fields being added. Stamped[T] is a generic class, like a C++ template.

MoreThe drone's clock wraps every 4.7 hours

Each packet carries the drone's own timestamp, which becomes the drone time in each stamped value. cflib unpacks the timestamp as 24 bits, so it restarts at zero every 16,777,216 counts. The code reads the counts as milliseconds since the drone booted, which makes that about 4.7 hours of drone uptime. That unit is marked to verify at the bench.

So the adapter keeps counting up across the wrap, using the previous drone time as the reference. A jump of more than half the range is a wrap. Anything smaller is an ordinary out-of-order packet.

MoreA broken estimate goes stale on purpose

If the drone sends a position estimate that isn't a finite number (NaN or infinity), the state block's callback, the function cflib calls with each of its packets, doesn't write it to the buffer. It throws it away, and logs a warning once per streak. The last finite estimate stays in the buffer and goes stale within 0.25 s, so the safety pre-check fails on it, and the failsafe sends a landing aimed at that last finite position.

But the drone's own estimate is NaN by then, so it can't follow that landing either. Today the operator's answer is the emergency stop, and a way to land a drone in that state is an open question (backlog #45). No field test so far has recorded such an estimate.

A velocity estimate that isn't finite is thrown away the same way, but the pre-check doesn't check whether the velocity estimate is stale, so a dropped one alone doesn't fail it.

MoreThe snapshot's time is read after the copy

The buffer copies every value, then reads its clock, all under the lock. Every value was stamped before it was stored, so no value in a snapshot is newer than the snapshot's time, and no age is ever negative.

Python note. with self._lock: takes the lock at the start of the block and releases it at the end, even when the block raises, like std::lock_guard in C++. The buffer's tests hold the lock themselves to prove that every read and write waits for it (test).

Why it's built this wayWhy a snapshot per tick?

If behaviors read shared values as they changed, one tick could see a mix of old and new values, and locks would spread through behavior code. A read-only snapshot per tick keeps every behavior in a tick on the same picture and confines thread safety to one hand-off: the copy at the start of the tick. It's also easy to build by hand in a test, and to replay from a recording.

Values that arrive together are written together, so no snapshot mixes two samples (test).

04

Commands

Every command starts an action and returns at once. None of them sleeps or waits for the drone, so the tick, 20 times a second, is never held up, and what a command did shows in later snapshots. The drone takes commands two ways: a setpoint stream, one low-level setpoint every tick, or the high-level commander, one move that the drone flies by itself. The drone follows one of them at a time, and the adapter hands it from one to the other: the setpoint priority.

The firmware's rules make the order of those sends matter, but the code has one path for each order. Every high-level move goes through one hand-over, and every motor stop through one function, so no caller can send them in the wrong order. Section 5 shows both orders, and a planted wrong order fails tests (section 9).

Why it's built this wayWhy no command sleeps

Whatever streams setpoints must send one every tick, or the firmware stops following it. Say land() slept until touchdown: the tick would stop for seconds, and the stream with it. So land() only starts the landing, and each tick moves it on (section 5).

The rule covers everything a tick runs. A behavior may not import a clock, so it has nothing to sleep on, and no command may sleep, wait for the drone or make any other blocking call. Only connect() and disconnect() may, and a program calls those, never a tick (section 7).

A fitness function checks it, reading the code: no drone interface method makes a blocking call but those two, and every blocking function in the adapter is reached from one of them. The known exception: a cflib send can wait up to 2 s during radio trouble.

05

The Bad-Flow Zone

Near the floor, the Flow deck's flow can't be trusted, so the estimated horizontal speed and position go wrong: the bad-flow zone. So take-off and landing cross it level. The adapter streams level setpoints, which hold roll and pitch at zero and set only a vertical speed, and hands over to the drone's own planner only once it's 0.15 m up, with flow. In a landing, the motors stop only when the down range confirms touchdown, or when the final descent's deadline says the drone must be on the floor.

MoreWhy the flow goes bad near the floor

It isn't known yet. Two possible causes, which may both play a part:

  • The firmware's flow model. It treats any height under 0.1 m as 0.1 m, which overstates the speed up to 4 times at the floor (ADR-0048, from the firmware's source).
  • Too little light. The Flow deck has no light of its own, so close to the floor the drone's own shadow may darken what the deck sees. Light does matter to it: with too little, it gives no flow at all. One night the room's lights gave a surface quality of 12-28, and a flashlight aimed at the take-off spot gave 87-103 (the living room's notes).

Light isn't the whole story: in the first flights' take-offs the speed estimate still went wrong near the floor with that flashlight (the hover test log, ADR-0048).

Why it's built this wayWhy cross the zone level?

A high-level move holds position by the horizontal speed estimate. In the zone that estimate is wrong, so the controller chases a speed that isn't there and slides the drone sideways. A level setpoint ignores the horizontal estimate: the drone moves only vertically, so it doesn't need the flow there.

The risk accepted with it: while level there is no position hold, so a small tilt error pushes the drone sideways. Ending the level part at a fixed 0.15 m keeps that drift small.

MoreThe hand-over at 0.15 m, in three sends

The climb ends at the first fresh down range at or above the final descent height, 0.15 m. With flow there, a hand-over gives the drone to its high-level commander. The order is the point: a streamed setpoint stops the high-level commander, and a stopped high-level commander turns the motors off once the stream is released. So the release must come after the move.

Python note. @contextmanager turns a generator into something a with block can use: the code before yield runs when the block starts, and the code after it when the block ends. go_to wraps its one high-level call in it, so no high-level move can skip the hand-over (commands.py 91-95).

Flow means a fresh velocity uncertainty under 0.03 m/s. Missing, stale, negative or not finite counts as no flow (bad_flow_zone.py 20-31, test).

MoreLanding: an approach, then the final descent

The landing approach is a high-level move straight down, aimed 5 cm below the final descent height. It isn't the firmware's own landing, which switches the motors off when it ends, even above the floor. The final descent then streams one level setpoint down each tick until touchdown is confirmed.

Python note. match and case compare a value against patterns, here the members of an Enum. It reads like a C++ switch on an enum class, with no fall-through between cases.

MoreThe motor stop, and the release after it

Every motor stop sends three things in order: the stop setpoint while a stream runs, the high-level stop, then the release of the setpoint priority. Without the release, the drone refuses the stopped high-level commander's motors-off setpoints, and a drone that still counts as flying locks once its setpoint is 2 s old. That's what happened before the release was added: in First flight 2, every arm request right after a flight was refused until the drone was power cycled (the session, ADR-0058).

MoreWhere the 2 s comes from

It's the firmware's limit, not this project's. The drone watches the age of its latest setpoint. While it counts itself as flying, a setpoint older than 500 ms raises a warning, and it levels out. Past 2000 ms it goes to a free-fall state, with the motors off, and from there it locks: it refuses to arm until it's power cycled.

A motor stop doesn't end this at once, because the drone still counts as flying for 2 s after the motors stop. The release lets new setpoints in, so the age stops growing.

06

May Be Flying

Stopping a flying drone takes a landing, but a landing sent to an armed drone on the floor would spin its motors up. So some commands must know whether the drone could be in the air, and the drone's own drone status can't settle it alone: it shows a take-off late, and keeps saying flying for 2 s after the motors stop. The adapter judges may be flying from what it sent and what the drone says, and when unsure, it says flying.

MoreEach rule, with its test
  • Rule 1. After our own motor stop, the snapshot says not flying while the status still says flying, and a hover then does nothing. test test: hover
  • Rule 2. An old on-the-floor status counts as unknown, so land() lands. One exactly at its age limit still counts, so land() only stops the motors. test test: at the limit
  • Rule 3. A land right after a take-off lands, before the status shows flying. One tick before the grace ends it lands, and at exactly its end it only stops the motors. test test: one tick before test: at the end
Why it's built this wayWhy the adapter judges it, not the safety layer

Just after a take-off, the drone status still says not flying and the down range still reads the floor, so nothing in the telemetry can tell. Only the adapter knows what it sent. So the safety layer approves a hover and a land without checking the status, and the adapter decides what they do. Every snapshot carries the answer, and the safety pre-check checks the velocity uncertainty only while it's true (section 3).

07

Connect and Disconnect

connect() and disconnect() are the only calls that may block: wait for the drone, or sleep, before they return. A program calls them, never a tick. Each wait for the drone has a time limit, so a drone that never answers ends in an error that says what to check, not a hang. Both end with the same careful link close: cflib's own close sends a zero-thrust setpoint first, which would drop a flying drone.

Why it's built this wayWhy these two calls block

Both run outside the ticks: connect() before the first one, disconnect() after the last. No setpoint stream is running on their thread, so a wait there starves nothing.

Until connect() returns, the program has nothing to do: a tick needs a drone that's ready, with every telemetry value arrived and its state known. If connect() returned at once and connected in the background, every tick would have to handle a drone that isn't ready yet, and a failure while connecting would turn up in some later tick rather than as connect()'s own error, with what to check. disconnect() must land the drone before it closes the link, and it ticks the landing itself while it waits.

cflib's own waits do run on background threads, each with a time limit, and connect() waits for them (below).

MoreWhy cflib's waits run on helper threads

cflib's connect waits with no time limit, and on Windows, Python 3.12 can't interrupt such a wait: Ctrl+C wouldn't get through. So each of cflib's blocking steps runs on a helper thread, and the calling thread waits for it in slices of 0.1 s. Between slices, Python handles the interrupt signal and the time limit is checked.

Python can't end a thread from outside, so a stuck step is never stopped, only abandoned: no longer waited for. Its thread is a daemon, so it doesn't keep the program alive. The adapter's own waits, for telemetry and for not flying, need no helper thread: a plain sleep ends at once on the interrupt signal.

MoreThe lock error that hid the interrupt signal

Thread.start() waits for the new thread to start. A Ctrl+C that lands at one moment inside that wait leaves a lock released, and Python then raises RuntimeError: release unlocked lock, with the KeyboardInterrupt only as its context. The program would report a lock bug, not the operator's Ctrl+C.

So run_with_time_limit looks for exactly that shape and raises the KeyboardInterrupt itself, after its except block: raised inside it, the lock error would become its context, and the Ctrl+C would read as one that came while handling another error.

Why it's built this wayWhy cflib's close_link() is never called on a drone that may be flying

cflib's close_link() sends a zero-thrust setpoint first, then closes the link. On a flying drone that setpoint cuts the motors. So while the drone may be airborne, or its state is unknown, the link part closes only the radio link: three of close_link()'s other steps, in the same order, and no setpoint reaches the drone.

A planted bug that always calls cflib's close fails tests in both connect() and disconnect() (section 9).

Python noteexcept Exception and except BaseException

Ctrl+C arrives as KeyboardInterrupt, which derives from BaseException but not from Exception. So except Exception catches ordinary errors and lets Ctrl+C through, and connect() uses that split: an ordinary error may be replaced by the lost link's error, which explains it, but the operator's Ctrl+C never is. A bare raise re-raises the error being handled, like throw; in C++.

Python notenonlocal: a closure that writes its outer variable

An inner function can read its enclosing function's variables, but assigning one would make a new local. nonlocal says the name belongs to the enclosing function, like a C++ lambda capturing by reference. Here the check keeps the list of missing values from its latest run, so the time-limit message names what was missing when the wait ran out.

08

Failures

While the link is up, every flying path ends in a landing or a motor stop, even after an error, and the log says what happened.

Why it's built this wayWhy a lost link raises at the next snapshot

cflib reports a lost link on whatever thread found it, even the tick's own, in the middle of a command. So the callback only records it. The error rises at a known place instead: the next snapshot, the first thing every tick does. Every tick takes its snapshot before it sends anything, so a lost link stops the tick before any of its commands goes out, and no command needs a check of its own. connect()'s waits keep a check of their own so they end at once.

Why it's built this wayWhy a sim clock

The adapter reads time only from the Clock it's given, never from the computer directly. A test gives it a sim clock, where sleeping jumps straight to the deadline: simulated time runs as fast as the code does, and every run gives exactly the same times. So a test can check a limit to the tick, at exactly its end and one tick before, with no flaky timing.

Python notepytest's fixtures and parametrize

pytest finds every function named test_… and runs it. Its arguments are fixtures: pytest builds each one by name before the test, such as a connected adapter or a fake cflib, much like a test fixture class's setup. @pytest.mark.parametrize runs one test once per value, with an id for each case in the report.
