# Decision backlog

Open architecture questions, in rough order of when they need deciding. When
one is decided it becomes an ADR in [`decisions/`](decisions/) and is removed
from this list. The ADRs keep their follow-up notes as history; this file is
the live list.

|---|---|---|---|
| 1 | **Drone interface design (in progress).** Decided so far, to be written up as one ADR when complete: (1) behaviors produce command *requests*; only the safety layer calls the drone interface (fitness function: behaviors never import it). (2) The interface has `take_snapshot()`; every adapter uses one shared `TelemetryBuffer` class (the single lock). (3a) Range readings use named fixed directions. (3b) Each reading distinguishes a distance, out of range (clear) and invalid (unknown). (3c) The downward reading is `ranges.down`, like the other directions; altitude comes from the position estimate's z, so there's no separate height field. (4) Command set: `connect`/`disconnect` (as a `with` block), `arm`/`disarm`, `take_off(height)`, `land`, `set_velocity(velocity, yaw_rate)` (steering mode, sent every tick), `move_to(position, duration)` (fast mode), `hover`, `emergency_stop`, `take_snapshot`. (5) Velocities are in the world frame; yaw is held fixed for now, so body and world directions coincide. Still open: (6) how refusals and failures are reported. Next-tick-only reporting was rejected: behavior trees need refusals during the same tick's search. Leading proposal (D): the safety layer offers synchronous, side-effect-free queries (e.g. `can_enter_fast_mode()`) that behaviors call during the search; the final verdict uses the same snapshot so it matches the query; physical outcomes (take-off done, link lost, crash) arrive in the next snapshot, like a BT task returning Running. | Conversation, 2026-10-19 | Next session |

| 3 | **Clock abstraction:** how real vs simulated time is provided, so tests and the simulator run faster than real time. | [ADR-0003](decisions/0003-tick-loop-timing-model.md) | Before the first tests |
| 4 | **Tick rate**, and telemetry periods per log block (the bandwidth budget). **Priority: responsiveness**, so the drone reacts as quickly as possible, especially to safety issues. Approach: design against a **latency budget** (sensor sampling, radio and queue, waiting for the tick, processing, command radio, physical response). Match the tick rate to the fastest telemetry that matters (ranges, position), since ticking faster than data arrives buys nothing, and per-tick commands share the radio. Measure the full chain in field-test stage 2. If radio and physical response dominate, see #10. | [ADR-0003](decisions/0003-tick-loop-timing-model.md) | Before the first behavior |
| 5 | **Tick timing strategy:** schedule ticks against absolute deadlines (no accumulated drift), sleep then spin-wait for the last moment, control Python's garbage collector (disable the cycle collector in flight, collect when a tick has spare time), and measure jitter continuously. Stay on Windows + Python unless measurements show jitter hurts; escalation paths are Linux (PREEMPT_RT) or the onboard reflex layer. | Conversation, 2026-10-19 | With the tick loop implementation |
| 6 | **Sensor pipeline:** where filtering happens (e.g. median of recent range readings) and where its history lives: the blackboard, or a perception step between snapshot and behaviors. | [ADR-0007](decisions/0007-snapshot-blackboard-telemetry-buffer.md) | Before the first behavior |
| 7 | **Safety-layer severity levels:** which faults are minor (blend back to steering mode), serious (stop and hover) or critical (land or e-stop), and the response for each. Include **ceiling protection**: a geofence maximum altitude (position estimate z, with a drift margin) plus a `ranges.up` check, with a generous margin for the ceiling effect (airflow pulls a drone toward a nearby ceiling). Relevant for the attic. | [ADR-0005](decisions/0005-control-modes-steering-and-fast.md) | Before the safety layer |
| 8 | **Fast-mode approval criteria:** measurable definitions for visibility, tightness of the space, latency and battery. | [ADR-0005](decisions/0005-control-modes-steering-and-fast.md) | Before fast mode is implemented |
