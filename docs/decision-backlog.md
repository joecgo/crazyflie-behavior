# Decision backlog

Open architecture questions, in rough order of when they need deciding. When
one is decided it becomes an ADR in [`decisions/`](decisions/) and is removed
from this list. The ADRs keep their follow-up notes as history; this file is
the live list.

| # | Open question | Came from | Needed by |
|---|---|---|---|
| 1 | **Frozen dataclasses by default?** The snapshot is written frozen provisionally ([ADR-0010](decisions/0010-code-foundations.md)). Decide after seeing how it reads in real code, both for the snapshot and as a default for other dataclasses. | [ADR-0004](decisions/0004-strict-typing-ruff-and-units-in-names.md), [ADR-0010](decisions/0010-code-foundations.md) | After reviewing the first snapshot code |
| 2 | **Tick rate**, and telemetry periods per log block (the bandwidth budget). **Priority: responsiveness**, so the drone reacts as quickly as possible, especially to safety issues. Approach: design against a **latency budget** (sensor sampling, radio and queue, waiting for the tick, processing, command radio, physical response). Match the tick rate to the fastest telemetry that matters (ranges, position), since ticking faster than data arrives buys nothing, and per-tick commands share the radio. Measure the full chain in field-test stage 2. If radio and physical response dominate, see #9. | [ADR-0003](decisions/0003-tick-loop-timing-model.md) | Before the first behavior |
| 3 | **Tick timing strategy:** schedule ticks against absolute deadlines (no accumulated drift), sleep then spin-wait for the last moment, control Python's garbage collector (disable the cycle collector in flight, collect when a tick has spare time), and measure jitter continuously. Stay on Windows + Python unless measurements show jitter hurts; escalation paths are Linux (PREEMPT_RT) or the onboard reflex layer. | Conversation, 2026-10-19 | With the tick loop implementation |
| 4 | **Sensor pipeline:** where filtering happens (e.g. median of recent range readings) and where its history lives: the blackboard, or a perception step between snapshot and behaviors. | [ADR-0007](decisions/0007-snapshot-blackboard-telemetry-buffer.md) | Before the first behavior |
| 5 | **Safety-layer severity levels:** which faults are minor (blend back to steering mode), serious (stop and hover) or critical (land or e-stop), and the response for each. Include **ceiling protection**: a geofence maximum altitude (position estimate z, with a drift margin) plus a `ranges.up` check, with a generous margin for the ceiling effect (airflow pulls a drone toward a nearby ceiling). Relevant for the attic. Include **landing that continues by the down sensor**: when touchdown isn't confirmed (ADR-0012), keep descending by the distance the down sensor measures until it confirms the floor, instead of holding where the drifted estimate thinks the floor is; with a last-resort motor cutoff if even that fails (a drop of a few centimeters is harmless). | [ADR-0005](decisions/0005-control-modes-steering-and-fast.md) | Before the safety layer |
| 6 | **Operator controls (human override).** Decided: the kill switch cuts the motors directly, bypassing the safety layer ([ADR-0013](decisions/0013-operator-kill-switch.md)). Still open: how the command is executed (a console command typed while the program runs, like a UE cheat; a single key; a gamepad button; or several). For a real emergency, one keystroke is faster than typing a command; whether the kill latches, refusing further flight until restarted; "land now" and "hover" keys (through the safety layer); a dead-man mode for first flights (motors run only while a button is held; the firmware supports this with its emergency-stop watchdog); a `tools/` emergency-stop script for when the main program has already exited. | Conversation, 2026-10-20 | Before field-test stage 0 (the bench checklist tests the e-stop) |
| 7 | **Fast-mode approval criteria:** measurable definitions for visibility, tightness of the space, latency and battery. | [ADR-0005](decisions/0005-control-modes-steering-and-fast.md) | Before fast mode is implemented |
| 8 | **Recorded flight data:** where it lives, what format, Git LFS or not (`.gitignore` currently blocks it). | [field-testing](field-testing/README.md) | Before field-test stage 1 |
| 9 | **Onboard reflex layer (hybrid):** move time-critical safety (obstacle stop, link-loss land) onto the drone as a firmware app, with behaviors staying on the PC. | Conversation, 2026-10-18 | After first real flights show where latency hurts |
| 10 | **Fast-mode override flag** that skips the approval checks (never the safety layer). Only if a real need appears; tests and simulation only. | [ADR-0005](decisions/0005-control-modes-steering-and-fast.md) | Only if needed |
| 11 | **Yaw control:** rotating the drone (movement doesn't need it, since quadcopters move in any direction by tilting). Possible reasons: facing people for interaction and personality, pointing a camera (AI deck, fixed forward-facing), sweeping the Multi-ranger's diagonal blind spots. Adding it means rotating range directions into the world frame in one place. | Conversation, 2026-10-19 | When a behavior needs it |
| 12 | **Mapping: Multi-ranger voxel occupancy grid → nav volume, with frontier exploration.** Range readings plus the position estimate build a 3D grid (occupied / free / unknown, held as probabilities because of noise and drift), updated continuously in flight. Then a game-style nav-volume pipeline: inflate by drone radius plus a drift margin, group free space, A* and path smoothing. Unknown space is blocked for travel but attractive for exploration (fly to the free/unknown frontier). Hand-authored maps rejected as too tedious. Open: grid resolution, probability model, octree vs plain grid, and whether yaw sweeps (#11) are needed for coverage. | Conversation, 2026-10-19/20 | Future feature |
| 13 | **Hide-and-seek and peek-a-boo with a young child: the project's main goal.** The drone hides and peeks out, or seeks. Needs: (a) a room map (mapping item) for hiding spots and line of sight; (b) tracking the child: a fixed room camera running person detection, calibrated to the drone's world frame (the same camera can also measure the drone's true position: ground truth for drift), possibly combined with the drone's own camera (AI deck) or a marker the child wears; (c) visibility: can the child see the drone? Ray casts through the map from the child's position; (d) choosing hiding spots by scoring candidate points for being hidden, a safe distance away and reachable, like UE's Environment Query System (EQS); (e) the game itself as a behavior tree: hide, wait, peek, react. **Safety first:** prop guards, a moving keep-out zone around the child enforced by the safety layer, slow speeds, development with stand-ins (a toy or an adult) long before any flight near a child, and no footage of the child in public material. | Conversation, 2026-10-20 | The long-term goal: after the vertical slice, hardware, and mapping |
| 14 | **Attic inspection: a visual map of a hard-to-reach attic, then finding anomalies such as wasp nests (stretch goal, after hide-and-seek).** The real-world counterpart is confined-space inspection drones. Shares the mapping core with hide-and-seek. Adds: (a) a camera, e.g. the AI deck (small and low-resolution; check payload, about 15 g in total, flight time, and whether it fits alongside the Flow and Multi-ranger decks); (b) the visual map is a 3D model of the attic, viewable in an editor (my own editor or a UE project), likely through the debug visualization (ADR-0014); (c) anomaly detection, likely offline on the PC from the collected images; (d) return-to-hatch and link-loss behavior, because a drone that lands in the insulation may be unrecoverable. Environment risks: darkness (the Flow deck needs light and texture: add lighting), loose blown-in insulation (downwash kicks it into motors and sensors; the soft surface confuses range readings), tight rafters and nails, wasps. **Safety:** a crashed LiPo battery left in insulation is a fire risk, so plan how to retrieve a crashed drone before flying up there. | Conversation, 2026-10-20 | Capstone: after mapping and return-home work in ordinary rooms |
| 15 | **Safety-query caching (watch item, not planned work).** Safety checks run twice per tick: once as a behavior's query, once at execution. If a check ever proves costly, cache its result for the tick (safe, because both use the same snapshot; clear at each new snapshot). It may never be needed: the checks may be too cheap to matter, and caching adds complexity that could cost more than it saves. Revisit as new behaviors are built, only when profiling shows a real cost. | Conversation, 2026-10-20 | Only if profiling shows a need |
