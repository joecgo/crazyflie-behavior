# Decision backlog

Open architecture questions, in rough order of when they need deciding. When
one is decided it becomes an ADR in [`decisions/`](decisions/) and is removed
from this list. The ADRs keep their follow-up notes as history; this file is
the live list.

| # | Open question | Came from | Needed by |
|---|---|---|---|
| 1 | **Frozen dataclasses by default?** The snapshot is the natural first candidate. Decide when the first snapshot code is written. | [ADR-0004](decisions/0004-strict-typing-ruff-and-units-in-names.md), [ADR-0007](decisions/0007-snapshot-blackboard-telemetry-buffer.md) | With the first snapshot code |
| 2 | **Tick rate**, and telemetry periods per log block (the bandwidth budget). **Priority: responsiveness**, so the drone reacts as quickly as possible, especially to safety issues. Approach: design against a **latency budget** (sensor sampling, radio and queue, waiting for the tick, processing, command radio, physical response). Match the tick rate to the fastest telemetry that matters (ranges, position), since ticking faster than data arrives buys nothing, and per-tick commands share the radio. Measure the full chain in field-test stage 2. If radio and physical response dominate, see #8. | [ADR-0003](decisions/0003-tick-loop-timing-model.md) | Before the first behavior |
| 3 | **Tick timing strategy:** schedule ticks against absolute deadlines (no accumulated drift), sleep then spin-wait for the last moment, control Python's garbage collector (disable the cycle collector in flight, collect when a tick has spare time), and measure jitter continuously. Stay on Windows + Python unless measurements show jitter hurts; escalation paths are Linux (PREEMPT_RT) or the onboard reflex layer. | Conversation, 2026-10-19 | With the tick loop implementation |
| 4 | **Sensor pipeline:** where filtering happens (e.g. median of recent range readings) and where its history lives: the blackboard, or a perception step between snapshot and behaviors. | [ADR-0007](decisions/0007-snapshot-blackboard-telemetry-buffer.md) | Before the first behavior |
| 5 | **Safety-layer severity levels:** which faults are minor (blend back to steering mode), serious (stop and hover) or critical (land or e-stop), and the response for each. Include **ceiling protection**: a geofence maximum altitude (position estimate z, with a drift margin) plus a `ranges.up` check, with a generous margin for the ceiling effect (airflow pulls a drone toward a nearby ceiling). Relevant for the attic. | [ADR-0005](decisions/0005-control-modes-steering-and-fast.md) | Before the safety layer |
| 6 | **Fast-mode approval criteria:** measurable definitions for visibility, tightness of the space, latency and battery. | [ADR-0005](decisions/0005-control-modes-steering-and-fast.md) | Before fast mode is implemented |
| 7 | **Recorded flight data:** where it lives, what format, Git LFS or not (`.gitignore` currently blocks it). | [field-testing](field-testing/README.md) | Before field-test stage 1 |
| 8 | **Onboard reflex layer (hybrid):** move time-critical safety (obstacle stop, link-loss land) onto the drone as a firmware app, with behaviors staying on the PC. | Conversation, 2026-10-18 | After first real flights show where latency hurts |
| 9 | **Fast-mode override flag** that skips the approval checks (never the safety layer). Only if a real need appears; tests and simulation only. | [ADR-0005](decisions/0005-control-modes-steering-and-fast.md) | Only if needed |
| 10 | **Yaw control:** rotating the drone (movement doesn't need it, since quadcopters move in any direction by tilting). Possible reasons: facing people for interaction and personality, pointing a camera (AI deck, fixed forward-facing), sweeping the Multi-ranger's diagonal blind spots. Adding it means rotating range directions into the world frame in one place. | Conversation, 2026-10-19 | When a behavior needs it |
| 11 | **Mapping: Multi-ranger voxel occupancy grid → nav volume, with frontier exploration.** Range readings plus the position estimate build a 3D grid (occupied / free / unknown, held as probabilities because of noise and drift), updated continuously in flight. Then a game-style nav-volume pipeline: inflate by drone radius plus a drift margin, group free space, A* and path smoothing. Unknown space is blocked for travel but attractive for exploration (fly to the free/unknown frontier). Hand-authored maps rejected as too tedious. Open: grid resolution, probability model, octree vs plain grid, and whether yaw sweeps (#10) are needed for coverage. | Conversation, 2026-10-19/20 | Future feature |
| 12 | **Safety-query caching (watch item, not planned work).** Safety checks run twice per tick: once as a behavior's query, once at execution. If a check ever proves costly, cache its result for the tick (safe, because both use the same snapshot; clear at each new snapshot). It may never be needed: the checks may be too cheap to matter, and caching adds complexity that could cost more than it saves. Revisit as new behaviors are built, only when profiling shows a real cost. | Conversation, 2026-10-20 | Only if profiling shows a need |
